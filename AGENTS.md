# manteion-go

Control plane of faults-lab (Go, Postgres). It stores rules, fault specs and experiments, serves every atropos SDK instance a desired-state document that the instance long-polls, runs experiment phases (freeze services, replay recordings, drive load through zeus), and records a fidelity verdict per frozen phase.

## Commands

```bash
make verify          # go build, gofmt -l (fails on output), go vet, go test
go test -race ./...
make integration     # MANTEION_INTEGRATION=1 MANTEION_TEST_DB=1 go test -count=1 -timeout 300s -p 1 ./...
make openapi         # regenerate docs/swagger.{yaml,json}
make openapi-check   # regenerate, then fail if the committed spec differs (CI's gate)
go run ./cmd/manteion
```

- Plain `go test ./...` passes while skipping every database-backed test. Store and orchestrator suites need `MANTEION_INTEGRATION=1`; many api and orchestrator tests also need `MANTEION_TEST_DB=1`. `make integration` sets both. CI's `go-integration` job sets only `MANTEION_INTEGRATION`, so the `MANTEION_TEST_DB` tests skip there too.
- The DB tests need Postgres: `colima start`, then `docker compose up -d postgres` (postgres:18-alpine on 5432). The default DSN is `postgres://manteion:manteion@localhost:5432/manteion?sslmode=disable`; set `MANTEION_DATABASE_URL` to use another. If another worktree's compose holds 5432, run a separate `postgres:18-alpine` on `127.0.0.1:55432` and point `MANTEION_DATABASE_URL` at it. Keep `-p 1`: the suites share one database and truncate every table between tests. Remove the container and volume afterwards.
- OpenAPI: `make openapi` regenerates the spec and `make openapi-check` then runs `git diff --exit-code -- docs/swagger.yaml docs/swagger.json`, which is what CI's `openapi-check` job runs. Needs `swag` v2.0.0-rc6 built with Go 1.27.3 or newer (swag parses the standard library of the Go it was built with, and go.mod says `go 1.27.3`) and python3 with PyYAML (install notes in the Makefile header). The spec is generated through the same module resolution as the build, so the local `go.work` must declare a `go` line of at least 1.27.3 (`go work edit -go=1.27.3`), as `go build` requires too.
- Go: go.mod says `go 1.27.3` with no toolchain line; CI uses `golang:1.27` and the Dockerfile `golang:1.27-alpine`. The pinned atropos trees (`atropos-pin`, `atropos-beds-pin`) say `go 1.25.5` and require older OpenTelemetry, gRPC and Prometheus versions than this module; minimal version selection builds them with this module's newer ones, which both resolutions compile.
- The experiment and phase handlers carry no swag annotations, so the spec does not cover them; the code is the reference.
- `go run ./cmd/manteion` listens on `:9090` (`MANTEION_ADDR`). The Kubernetes manifest sets `:8080`, which is why other repos say `manteion:8080`. With `MANTEION_DEMO=true` it also listens on `:8090` (`MANTEION_DEMO_ADDR`, see "Demo mode"); the manifest turns demo mode on.

## How this tree resolves atropos

manteion compiles against a different atropos-go depending on how it is built. Check which one before trusting a fault-catalog or wire behaviour.

- Local `go build` / `go test`: the untracked, gitignored `go.work` replaces atropos with `faults-lab/worktrees/atropos-pin`.
- Docker and skaffold: `go.mod`'s `replace => ../atropos-go`, which from this tree is `worktrees/atropos-go`, a symlink to `worktrees/atropos-beds-pin`. The Dockerfile and `skaffold.yaml` also assume the repo directory is named `manteion-go` beside `atropos-go` (`COPY manteion-go/`, `dockerfile: manteion-go/Dockerfile`), which is not true for this worktree. The lab image is therefore built from a staging directory made by `service-beds/scripts/lab-up.sh`: `git archive` copies of manteion-go and atropos-go as `manteion-go/` and `atropos-go/`, with modules vendored from a local file GOPROXY, cross-built for linux/amd64.
- CI clones atropos-go `develop`, a third version.
- The fault catalog validates through atropos `faultparams`, so `network/packet_loss` and `mechanism: netem` are accepted by a beds-pin build and rejected (422) by a `go.work` build.
- The README's "SDK dependency" section (atropos required by tag, no replace, `GOPRIVATE`) is wrong; `go.mod` has the replace.

## Where the code misleads

- Nothing is pushed to SDK instances. Rules, fault configs, `freeze_cfg` and replay sets reach them only through the polled document. `internal/atropos` is read-only (`GetRules`, `GetFault`, `GetCacheBoxStats`, `GetCacheBoxFidelity`); README line 35 still says write methods exist. `docs/2026-06-wiring-audit.md` and `docs/architecture-diagram.html` still draw pushes.
- Desired state needs the phase and its experiment both `running`: `RuleRepo.ForService` and `ExperimentRepo.ListRunningPhases` (the source of the cache-box rule, `freeze_cfg` and `replay_set`) join on the experiment's status. A cancel or stop that fails partway (a crash after the experiment's terminal CAS, or a `finishPhase` error) still leaves the phase `running`, `paused` or `draining` under an ended experiment. Nothing is served for it any more, but no exit bump follows until manteion next starts, so held polls drop it only when their wait ends. At start-up `Recover` skips every such phase (`ListStrandedPhases`) through `finishPhase` in a goroutine: its load is stopped, its fault events closed, its services bumped. A zeus it cannot reach then is only logged, so a run zeus still holds goes on to its configured end. `Recover` also moves every `pending` phase of an ended experiment (`ListPendingPhasesOfEndedExperiments`) to `skipped` with the plain status transition a cancel uses, so a phase added to an experiment after it ended is skipped at the next start. On a cancel the experiment's CAS lands before `finishPhase` stops the load, so an instance whose held poll re-materializes in between drops the phase's rules and freeze while load still runs (a skipped phase is not harvested).
- An interrupted resume is completed, not failed. Pause leaves the old zeus handles on `phase_workflows`; if manteion restarts during a resume's convergence wait, `Recover` sees a running phase with drivers and completes it over pre-pause traffic. The "entry interrupted by a manteion restart" guard only catches fresh entries.
- The phase-level API bypasses most of the experiment state machine and admission. `POST /experiments/{id}/phases` adds phases to running or finished experiments; a phase added to an experiment that has already ended can no longer be started (the start route refuses it, below) and stays `pending` until the next start-up's `Recover` marks it `skipped`. `POST /experiments/{id}/phases/{phaseId}/start` and `POST /phases/{phaseId}/resume` refuse with 409 `invalid_state` (carrying the experiment's status) unless the phase's experiment is `running`; the dataset preflight and, for a pending phase, the cache-box rule agreement answer their 422 first. That check holds no lock, so a cancel can land between it and the phase's claim, and what follows depends on the order: if the cancel skips the still-pending phase first, the claim fails and the start answers 409 `invalid_state`; if the claim lands before the cancel reads the phases, the cancel ends the phase (`skipped`) and the entry starts no load; but if the claim lands after the cancel has read the phase as `pending` and before its skip, the skip matches nothing and the phase stays `running` under the cancelled experiment: its entry goes on and starts its load, nothing is served for it (the experiment no longer runs), and the poller completes and harvests it when the load ends (or the next start's `Recover` skips it as stranded). Neither route checks service overlap. Pausing and stopping a single phase work under any experiment status, which is how a phase stranded under an ended experiment is cleaned up; stop defaults to `completed`, which harvests the phase, so pass `?status=skipped`. Admission itself is check-then-act without a lock and passes when its reads fail.
- `DELETE` on an experiment or phase works in any status and tears nothing down: zeus load keeps running, the poller ticks until its safety-net deadline (at least 30 min), and there is no exit bump, verdict or harvest.
- Fault configs are not phase-scoped. `fault_configs.phase_id` is only a tag; a config with `duration_ms: 0` outlives its phase and experiment, and a config fired at a frozen service bypasses admission and the verdict.
- The kill switch (`POST /sdk/instances/{id}/kill-switch`) acts on the whole service, not the instance. It disables rules permanently (there is no un-kill) and cancels fault configs, but leaves a running phase, its load, its cache-box rule and freeze in place, and the OPA harness can re-enable rules on its next tick.
- Pausing a recording (`persist_cache`) phase loses records: the SDK's pause-triggered flush is answered `409 phase_not_recording`, which the SDK treats as terminal. The final drain then likely reports the baseline degraded.
- A frozen phase is set `running` before its replay-set artifact exists, so an instance polling in that window gets `freeze_cfg` without a replay set and fails closed (synthetic 503s).
- Convergence means "observed the generation", not "applied it". `observed_errors` and `unsupported` do not block, and `internal/desired/capabilities.go` drops the `netem` capability and filters by category only. A phase whose fault no instance can execute still converges and is recorded as a fault phase.
- Experiment start answers 202 even when the first phase failed to converge, after blocking up to `MANTEION_CONVERGE_TIMEOUT` (30 s). Only resume and phase start return `504 not_converged`. Experiment pause, resume and cancel wait behind an in-flight entry because they take the same per-experiment lock.
- Verdicts exist only for completed frozen phases. They check replay misses, uncommitted preload, degraded baseline, missing telemetry and collision rate; there is no dropped-iteration check, and `INVALID` is stored without refusing anything.
- For a workflow run, `phase_workflow_results.error_count` is `max(0, requests_sent - requests_ok)` (HTTP failures) and `error_rate` is `error_count / requests_sent` (`internal/orchestrator/harvest.go`). zeus's `requests_dropped` is k6's dropped iterations (load the executor could not deliver), not failed requests; it stays only in `raw_metrics`.
- zeus forgets runs and attacks when it restarts. A workflow run's `GET /runs/{id}` 404 (`zeus.ErrRunNotFound`) fails the phase on the next poll with "zeus no longer knows run ...". At start-up `Recover` likewise counts a run as lost only on that 404; any other error (connection refused while zeus restarts, a timeout, a 5xx) is retried, 5 s per call with backoff 1, 2, 4, 8 s, until one deadline that all of `Recover`'s run checks share (`WithReconcileBudget`, 20 s from the start of `Recover`); then, or for a run reached after the deadline without a call, the poller takes the run over. `Recover` runs before the API listens, so with zeus down its run checks delay start-up by about 20 s at most, however many runs are in flight. `Recover` never starts or fails a phase before it returns: a phase whose drivers are all lost is failed, and the next phase of an experiment that stalled between phases is started, in goroutines, and a shutdown during the driver checks fails nothing. That next phase's entry still waits at most `MANTEION_CONVERGE_TIMEOUT` (30 s) for instances whose polls failed during the restart, and the SDK retries a failed poll only after 20, 40, then up to 60 s. So after a long restart the entry can time out, or a frozen phase fail at once when its service's instances have missed polls for 60 s; a non-frozen phase can also pass while those instances are stale and get its rules only at their next poll. Attacks are still reconciled outside that deadline with three quick tries in which any error, connection refused included, counts as lost, so a phase whose only drivers are attacks fails if zeus is down when manteion starts, and a zeus that accepts connections but never answers holds start-up up to about 90 s per attack. An attack's `GET /attacks/{id}` 404 is still treated as transient by the poller, so a phase whose attack zeus lost hangs until `max(30 min, duration + 5 min)` and fails with a misleading "safety-net deadline" reason. Stopped runs get no zeus stats snapshot, so no `phase_workflow_results` row is written.
- The zeus events proxy shares the zeus client's 30 s total timeout and copies without flushing, so `/api/v1/zeus/runs/{id}/events` is cut at 30 s and arrives buffered.
- State lost on restart: cache-store dedup and received counts, collision stats, claims, pollers. SDK retries after a restart can append duplicate batches; the drain gate then usually times out as degraded. A crash after a phase's terminal CAS loses its verdict, harvest and fault-event closing for good. `Recover` reads at most 200 running experiments.
- Some document changes do not bump the generation: a fault config's time-based expiry (until the reaper's bump), a fault-spec edit, attaching or detaching phase rules, and deleting a phase or experiment. Held polls see them only when their wait ends, within one wait.
- An enabled rule attached to no phase is live immediately. Rules are created disabled; `tools/expctl` creates them disabled, attaches them, then enables them.
- `readJSON` ignores unknown fields and `MatchCriteria.Validate` is never called, so typos in request bodies are dropped silently. The UI's `match_ast` is dropped the same way.
- `docs/design/DESIGN-CALLS-cachebox-2026-07-30.md` in the knowledge base reads D4, D6 and D8 as adopted; none is implemented as written. Nothing marks a recording degraded on `Recover` (D4); degraded baselines are allowed only by the env var `MANTEION_ALLOW_DEGRADED_BASELINE`, not a per-run flag (D6); admission refuses overlapping service footprints, not a second experiment per mesh (D8).
- OPA harness (`MANTEION_POLICY_ENGINE=rego`): a policy cannot act while Prometheus or Loki is down, so a "safety brake" policy fails static. Its input has no experiment or phase state and mutations are only scope-checked by service, so a policy can toggle phase-attached rules mid-phase. The example queries in `docs/opa-harness.md` never match (wrong service name, log body and span name).
- Stale targets: every `tools/expctl/examples/*.yaml` targets the retired VM1, and `tools/expctl/README.md` port-forwards on vm1. `exp3-latwave.yaml` fails with 422 after creating its specs and rules, leaving them behind.

## Demo mode

`MANTEION_DEMO=true` runs `internal/demo`, a public demo that runs one scenario of a fixed catalog at a time, wired in `cmd/manteion/main.go`. The README's environment table has its settings, and its "Demo API" section the routes, the POST body and the run's fields.

- Its own listener: a second `http.Server` on `MANTEION_DEMO_ADDR` (`:8090`), built by `newDemoServer`, with its own `http.ServeMux` and only the seven routes under `/api/v1/demo/` (health, state, the scenario list, POST runs, recent runs, a run, a run's event stream). Every other path there is 404 JSON, and none of the operator API is reachable through it; the demo routes are not on the operator listener either. The server answers no `OPTIONS *` itself (`DisableGeneralOptionsHandler`) and speaks HTTP/1.1 only. The demo routes carry no swag annotations and are not in `docs/swagger.*`; `internal/demo/contract.go` is their reference.
- The catalog (`internal/demo/scenarios.go`) is compiled in: no route, file or environment variable adds to it. `GET /scenarios` answers it from memory (no store call) and counts as a read of the client's 120 a minute. A scenario id is never reused for a changed scenario: a run's experiment description names its scenario id, and a run read back from the database is shown as the catalog's current definition of that id builds it, so an id edited in place would relabel its past runs. A run of a scenario since removed from the catalog reads back with its stored id and each phase's fault, target and intensity from the run's own rules and their specs; a run of build 2's shape (one rule `demo-run-<run id>`, phases `plain`, `catalog-latency-50ms`, `plain-end`) reads back as build 2 served it, with `scenario: ""`.
- POST's body, read only after the edge secret and the client key: at most 1 KiB within 3 s (`readBody`), then `scenarioOf`. No body, only JSON whitespace, or `{}` is the default scenario; `{"scenario":"<id>"}` with `<id>` a JSON string exactly equal to a catalog id (no case folding or trimming; a JSON escape counts as the character it decodes to) is that scenario. Anything else is 400 `bad_request` before the lab's state, the client's run, its enqueue limit or the line are looked at, so nothing is queued or counted: another key, the key twice (even with equal values), a non-string value (`null` included), an unknown or empty id, data after the object, a body that is not JSON or not UTF-8, one over the cap. The parser walks tokens because `encoding/json` matches keys case-insensitively and keeps the last of a duplicate key. `Content-Type` is not read (the edge sends none). Nothing of a body is echoed or logged.
- A run: three phases, `baseline`, `memory`, `cpu`, 40 s each; experiment `demo-run-<run id>`; two rules, `demo-run-<run id>-memory` and `demo-run-<run id>-cpu`, each created disabled and attached to its own fault phase, with one fault spec per distinct fault (`demo-<kind>-<target>-<intensity>`), reused and checked against the catalog before each build. The worker's switch owns the two rules as a set: `on` switches both before the experiment starts and, if the second fails, switches the first off again and the run does not start; `off` writes only the rules not yet confirmed off, so a retry after a partial failure touches only the rule still on, and the next run is held (`accepting: false`) until both are confirmed off. Preflight checks the chosen scenario's targets and dataset; health's `target` needs an alive instance of every catalog target and `load_generator` a usable dataset of every catalog workload, so health can pass only when any scenario's run could.
- Proof that a fault ran: when a phase completes, the worker asks Prometheus, with fixed queries built only from constants, a catalog target and two integers, for the target's own process metrics by its `service` label over that phase's own window: W its length in whole seconds, read L seconds back with PromQL's `offset`, L the whole seconds from the phase's end to the read (no `offset` when L is 0, and a read before the end, a clock behind the store's, counts as 0). Memory, in bytes: the peak during the memory phase, `max_over_time(process_resident_memory_bytes{service="<target>"}[<W>s] offset <L>s)`, against the lowest during baseline, `min_over_time(...)` of the same over the baseline phase; peak and floor, not averages, because a previous run's memory is released 24 to 41 s (sometimes minutes) after its memory phase, so it can still be held when the next run's baseline starts, and averages would then shrink or invert the rise of a fault that ran. CPU, in cores: `rate(process_cpu_seconds_total{service="<target>"}[<W>s] offset <L>s)` over the cpu phase against the same over the baseline phase. The baseline's figures are read when it completes and kept on the run. The phase's `measure` holds both figures (`value` the phase's, `baseline` the baseline's) and `fault_observed` is true when the rise over baseline reaches 6694502 bytes (memory) or 0.0503 cores (CPU), false when it does not, and null when either figure is missing (failed, empty, NaN or infinite answer, no answer within `QueryTimeout`, or the phase's end read more than 300 s after its time); a proof never fails or holds up a run. The figures are not stored: they live only in this process's views, so a run read back from the database (every run after a restart) shows `measure` with both figures null and `fault_observed` null. The lab has no container (cAdvisor) series, so these are the Go client's process collector's. Live `sample` events add the running phase's target's CPU (`rate(...[20s])`) and resident memory.
- Nothing may wrap the demo handler unless it implements `Unwrap`: both the event stream and the unread-body guard reach the connection through `http.NewResponseController`, and a wrapper that hides it turns streams into 500s and lets an unread body hold a connection until `ReadTimeout`.
- Start-up order (`startDemo`): `orch.Recover`; then `d.SwitchOffAll`, called once (every enabled `demo-run-*` rule off, database only; the package detaches it from the signal and bounds it at 30 s itself), before either listener starts, because the operator listener serves desired state and a rule left on by a kill would be served the moment the SDKs can poll; if the signal has come by the time it returns, nothing more starts (no listener, no sweep, no worker) and main goes straight to its shutdown; otherwise both listeners; then, in one goroutine, `d.Sweep` under 2 minutes derived from the signal's context (it cancels leftover demo experiments, and a cancel waits for the fleet to converge, which needs the operator listener up), then, once it has returned, `d.Run`. Until the sweep has run, POST answers 503 and state says `accepting: false`. A failed switch-off or sweep is logged and start-up goes on. One Info line, `demo mode on`, names the settings in force (address, poll interval, run cap, queue capacity), never the secret. Nothing else may call `Run`, `Sweep` or the package-level `Sweep`/`Retain`.
- Shutdown order (`shutdownInOrder`): on the signal, `d.Shutdown` first, under its own 15 s, while both listeners still serve: it switches off, all at once, the rules of the current run and of an ended run whose switch-off is still pending (the SDKs pick that up only from the operator listener) and ends every event stream. Then the demo server's and the operator server's `Shutdown` under the existing 10 s budget, then the harness wait. The other order makes a server's `Shutdown` wait out the streams' 10-minute maximum age. The manifest's `terminationGracePeriodSeconds: 45` covers 15 + 10 s.
- Client rule: `X-Demo-Client` is honoured only on a request that also carries a valid `X-Demo-Edge-Secret` (`MANTEION_DEMO_EDGE_SECRET`, from the Secret `manteion-demo-edge` that service-beds' `scripts/lab-demo-secret.sh` creates). Every request without it is the one shared client `local`, whatever it sends. The secret is never logged.
- Run lookups are bounded (`internal/demo/lookups.go`), so public reads cannot fill the database pool. A run in the line or among the last ended runs is answered from memory. Anything else goes through a run index: the ids of the demo experiments the start-up sweep and each retention pass list, plus every run that ended in this process. While the latest listing completed, an id outside the index is 404 with no query. At most two database lookups run at once (`maxDBLookups`); a request that finds both taken is answered 503 `unavailable` at once, so a client should retry a 503 on a run read. The view of a run whose experiment and phases have all ended is kept (32 at most) until retention removes the run.
- `MANTEION_POLL_INTERVAL` is not a demo setting: it is the orchestrator's zeus poll tick (default 15 s) and applies to every experiment, operators' included. The lab's manifest sets 2 s, so a demo phase ends within 2 s of its load.
- A run's life in the log, at Info: `demo: run picked up`, `demo: run built`, `demo: rule switched on` (once per rule), `demo: starting the run's experiment`, the orchestrator's phase lines, `demo: fault phase measured` (once per fault phase, with `run_id`, `phase`, `metric`, `value`, `baseline` and `fault_observed` true, false or unknown: the memory phase's while the run goes on, the cpu phase's usually after the switch-off, because the last phase's end is read with the experiment's), `orchestrator: experiment finalized`, `demo: rule switched off` (once per rule, with its `reason`: completed, failed, cancelled, timed out, shutdown, start-up or retention), `demo: run ended`, then `demo: retention done`. A proof figure that could not be read is a Warn line, `demo: a figure of a fault phase's proof is null`, with the run, the phase, the metric and a fixed `problem` (and the query's error, in this log only). A switch-off that fails is a Warn line per rule (the first, then at most one a minute, then the Info line of the one that lands), a switch-off that found a rule already off or gone is Debug, and so is the request line of a refusal (400, 403, 404, 429), a bad POST body's included.
- Policy engines must be off: start-up refuses `MANTEION_DEMO=true` with `MANTEION_POLICY_ENGINE` `rego`, `on` or `threshold` (`demoModeCheck`), because an engine switches rules on and off by itself and the demo owns its run's rules.
- `Deps.Prom` must be a working client or a true nil interface, never a typed-nil pointer (a typed nil passes the nil check and every sampling round panics). `main` passes `promql.NewClient`'s, which is never nil.
- Tests: `internal/demo`'s database tests, like the orchestrator's and the store's, skip without the test database and then prove nothing. Run them with `make integration` against Postgres (see Commands). The worker's `bg` WaitGroup counts every goroutine of the worker and its sampler that can outlive the call that started it (starts, late cancels, switch-off retries, watchdogs, Shutdown's switch-offs, proof and sample queries still in the client); a query that had not reached the client when its read or round was cut short never asks. Nothing in the package waits on `bg`: a test does, and only after `Run` (and, for a `Demo`, the sampler) has returned, since until then the group can still be added to.

## Conventions

- Schema epoch 2: migrations in `internal/db/migrations.go` are append-only, and `Migrate` refuses a database whose history it does not recognize. Resetting means dropping the database.
- PG enums: `internal/store/enum_parity_test.go` pins the Postgres labels to `model.EnumValues`; a new enum value needs a migration and the model change together.
- Handler tests are DB-gated because `Server.experiments` is a concrete `*store.ExperimentRepo` with no fake. `experiment_phases_position_unique` is DEFERRABLE, so its violations surface at `Commit()`.
- Classify errors with `errors.As` / `errors.Is` on the typed errors, never by parsing the `error` string.
- The fix "stop counting k6 dropped iterations as request errors" is on this branch (cf3abfa, cherry-picked from git.ucsc.edu `origin/develop`). GitHub's `develop` does not have it.
